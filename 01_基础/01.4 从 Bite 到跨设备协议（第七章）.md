# 第 7 章：DER / PEM / Key / Signature / Certificate

这一章把前面学过的 `Raw Binary / Base64 / TLV / ASN.1 / DER` 真正放进密码工程里。

> [!important] 本章主线  
> **密码学对象、对象结构、二进制编码、文本包装必须分层理解。**
>
> 同一把密钥、同一个签名、同一张证书，可以因为结构和外部表示不同而呈现完全不同的 Byte。

---

## 第 7 章 · 第 1 课时

### DER 与 PEM：同一份数据为什么会有两种长相？

先建立最重要的关系：

```text
密码学对象
    ↓
ASN.1 结构
    ↓ DER 编码
DER Binary
    ↓ Base64
Base64 Text
    ↓ 加 BEGIN / END 标签
PEM
```

### 一、DER 是 Binary

DER（Distinguished Encoding Rules）是 ASN.1 的一种编码规则。

假设 ASN.1 逻辑结构：

```text
SEQUENCE {
    version INTEGER,
    data    OCTET STRING
}
```

数据：

```text
version = 1
data    = AA BB CC
```

DER 可以编码为：

```text
30 08
   02 01 01
   04 03 AA BB CC
```

这里看到的 `30 08 02 01 ...` 是 **Hex Dump**。

文件中真正保存的是：

```text
0x30
0x08
0x02
0x01
...
```

也就是二进制 Byte。

> [!note] DER 与 Hex Dump  
> `DER = Binary`
>
> `30 82 03 21 ...` 只是人类查看 Binary 时使用的十六进制显示形式。

---

### 二、PEM 是 DER 的文本包装

DER 是 Binary，而很多文本环境更适合处理 ASCII，因此可以先：

```text
DER
 ↓ Base64
ASCII Text
```

然后加上对象标签：

```text
-----BEGIN CERTIFICATE-----
MIIC...
-----END CERTIFICATE-----
```

所以常见 PEM 可以理解为：

```text
PEM
=
BEGIN 标签
+
Base64(DER)
+
END 标签
```

PEM 本身不是密码算法，也不是“证书算法”。

下面这些对象都可能使用 PEM：

```text
-----BEGIN CERTIFICATE-----

-----BEGIN PUBLIC KEY-----

-----BEGIN PRIVATE KEY-----

-----BEGIN EC PRIVATE KEY-----

-----BEGIN CERTIFICATE REQUEST-----
```

真正的对象结构仍然要看 Base64 解码后的 DER。

---

### 三、DER 和 PEM可能表示同一个对象

例如同一张 X.509 Certificate：

```text
X.509 Certificate
        │
        ↓ DER
   DER Binary
      │     │
      │     └── Base64 + PEM Wrapper
      │
    .der              .pem
```

因此更准确地说：

```text
Certificate = 对象

ASN.1       = 描述对象结构

DER         = 对象的二进制编码

Base64      = Binary → Text

PEM         = Base64 文本包装
```

---

### 四、从 PEM 公钥一路拆到底

看到：

```text
-----BEGIN PUBLIC KEY-----
MFkwEwYHKoZIzj0CAQYI...
-----END PUBLIC KEY-----
```

应该这样理解：

```text
PEM
 ↓ 去掉 Header / Footer
Base64
 ↓ Decode
DER
 ↓ ASN.1 Parse
SubjectPublicKeyInfo
 ├── AlgorithmIdentifier
 └── subjectPublicKey BIT STRING
          ↓
       EC Point
          ↓
      04 || X || Y
```

如果业务接口最终只需要裸 SM2 公钥，还可能继续得到：

```text
X || Y
```

---

### 五、扩展名并不绝对可靠

例如：

```text
.pem
.der
.key
.crt
.cer
```

只能作为提示。

`.crt` 可能是 PEM，也可能是 DER。

真正可靠的识别方式是：

```text
检查内容
 ↓
是否存在 BEGIN / END
 ↓
Base64 是否合法
 ↓
DER 是否能解析
 ↓
ASN.1 结构是否符合预期
 ↓
OID / Key Length / Object Type 是否正确
```

> [!tip] 工程思维  
> 自动识别格式不是“猜扩展名”，而是**逐层解码、逐层验证**。

### 本课小结

```text
DER = ASN.1 对象的二进制编码

PEM = Base64(DER) + 文本标签
```

以后拿到密码数据，先问：

```text
对象是什么？
结构是什么？
编码是什么？
外部表示是什么？
```

## 第 7 章 · 第 2 课时

### Key：Raw Key、EC Point、SPKI、PKCS#8

### 一、SM2 公钥最底层是 EC Point

椭圆曲线公钥：

```text
P = (X, Y)
```

SM2 使用 256-bit 坐标，因此通常：

```text
X = 32 Byte
Y = 32 Byte
```

最直接的 Raw 表示：

```text
X || Y
```

长度：

```text
64 Byte
```

标准未压缩 EC Point：

```text
04 || X || Y
```

长度：

```text
1 + 32 + 32 = 65 Byte
```

其中：

```text
04 = Uncompressed Point
```

还可能遇到压缩点：

```text
02 || X
03 || X
```

长度为 33 Byte。

> [!important] 64 Byte 与 65 Byte  
> `X || Y` 和 `04 || X || Y` 可以描述同一个点，但 Wire Format 不同。
>
> 协议必须明确究竟使用哪一种。

---

### 二、只有 X/Y 还不够标准化

单独看到：

```text
04 || X || Y
```

程序仍然不知道：

```text
这是哪种算法？
使用哪条曲线？
```

因此标准格式会携带算法信息。

最常见的公钥结构：

```text
SubjectPublicKeyInfo
```

简称：

```text
SPKI
```

可以抽象为：

```text
SubjectPublicKeyInfo
├── AlgorithmIdentifier
│   ├── algorithm OID
│   └── parameters
└── subjectPublicKey BIT STRING
        ↓
     EC Point
```

所以 SPKI 可以理解为：

```text
算法信息
+
真正公钥
```

---

### 三、`BEGIN PUBLIC KEY` 通常对应 SPKI

完整层次：

```text
-----BEGIN PUBLIC KEY-----
        ↓
      Base64
        ↓
       DER
        ↓
SubjectPublicKeyInfo
 ├── AlgorithmIdentifier
 └── BIT STRING
        ↓
     04 || X || Y
```

因此 PEM 公钥比 64/65 Byte Raw Key 长很多，是正常的。

里面还保存了：

```text
ASN.1 Tag
Length
Algorithm OID
Curve / Parameters
BIT STRING
```

---

### 四、私钥最底层是 `d`

SM2 私钥本质：

```text
Private Key = d
```

通常：

```text
32 Byte
```

因此可以先建立：

```text
Raw Private Key ≈ 32 Byte

Raw Public Key  ≈ 64 Byte
                 X || Y
```

但是单独的一串 32 Byte 自己不会告诉你：

```text
它是 SM2 私钥？
对称密钥？
Hash？
随机数？
其他 EC 私钥？
```

Binary 本身没有语义。

---

### 五、ECPrivateKey 与 PKCS#8

传统 EC 私钥结构可以抽象成：

```text
ECPrivateKey
├── version
├── privateKey OCTET STRING
├── parameters OPTIONAL
└── publicKey OPTIONAL
```

因此：

```text
-----BEGIN EC PRIVATE KEY-----
```

通常对应：

```text
PEM
 ↓
DER
 ↓
ECPrivateKey
```

而：

```text
-----BEGIN PRIVATE KEY-----
```

通常表示 **PKCS#8**。

PKCS#8 是更通用的私钥容器：

```text
PrivateKeyInfo
├── version
├── AlgorithmIdentifier
└── privateKey OCTET STRING
```

对于 EC / SM2，可能继续嵌套：

```text
PKCS#8
├── AlgorithmIdentifier
└── OCTET STRING
      ↓
   ECPrivateKey
      ↓
      d
```

所以一个私钥里看到两个 `OCTET STRING` 并不奇怪。

它们属于不同层。

---

### 六、BIT STRING 中的 `00`

ASN.1 `BIT STRING` 的内容开头通常包含：

```text
unused bits
```

例如：

```text
03 42 00 04 [X] [Y]
      ↑  ↑
      │  └── EC Point Prefix
      │
      └──── BIT STRING unused bits
```

因此：

```text
00
```

属于 ASN.1 BIT STRING。

而：

```text
04
```

属于 EC Point Encoding。

不能混在一起。

---

### 七、Raw / DER / PEM 不是同一级分类

例如同一把 SM2 公钥：

```text
数学对象
   ↓
EC Point
   ↓
04 || X || Y
   ↓
SPKI
   ↓
DER
   ↓
Base64
   ↓
PEM
```

因此：

```text
64 Byte
65 Byte
SPKI
DER
PEM
```

不是五把不同的钥匙。

而是：

```text
同一个对象
↓
不同结构层
↓
不同编码层
↓
不同外部表示
```

### 本课小结

```text
d                  → 私钥本体

X || Y             → Raw 公钥

04 || X || Y       → 未压缩 EC Point

SPKI               → 算法信息 + 公钥

PKCS#8             → 算法信息 + 私钥

DER                → ASN.1 Binary

PEM                → DER 的文本包装
```

## 第 7 章 · 第 3 课时

### Signature：`r`、`s`、Raw 与 DER

### 一、签名对象本身

SM2 / ECDSA 风格签名最终得到两个整数：

```text
Signature = (r, s)
```

对于 256-bit 曲线，工程中常把每个整数保存为固定：

```text
32 Byte
```

于是：

```text
Raw Signature
=
r[32] || s[32]
```

总长度：

```text
64 Byte
```

如果转成 Hex String：

```text
64 Byte
→
128 个 Hex 字符
```

---

### 二、DER Signature

ASN.1 可以把签名定义为：

```text
SEQUENCE {
    r INTEGER,
    s INTEGER
}
```

DER 编码大致：

```text
30 xx
   02 xx [r]
   02 xx [s]
```

典型情况：

```text
30 44
   02 20 [r 32 Byte]
   02 20 [s 32 Byte]
```

总长度：

```text
70 Byte
```

---

### 三、为什么 DER Signature 不是固定长度？

因为 DER 里的 `r / s` 是：

```text
ASN.1 INTEGER
```

而不是：

```text
固定 32 Byte Array
```

ASN.1 INTEGER 是有符号整数，而且 DER 要求最短规范编码。

#### 最高 bit = 1

例如：

```text
80 12 34 ...
```

如果直接作为 INTEGER，可能会被解释成负数。

因此要补：

```text
00 80 12 34 ...
```

于是 32 Byte 可能变成 33 Byte。

#### 存在不必要的前导 00

Raw 固定宽度可能是：

```text
00 12 34 ...
```

DER 会删除不必要的前导 `00`：

```text
12 34 ...
```

于是 32 Byte 也可能变成 31 Byte。

所以：

```text
Raw Signature
=
固定宽度 r + 固定宽度 s
=
64 Byte
```

而：

```text
DER Signature
=
SEQUENCE(
    INTEGER r,
    INTEGER s
)
```

长度是可变的。

常见看到：

```text
70 / 71 / 72 Byte
```

并不奇怪。

---

### 四、DER → Raw

正确过程：

```text
解析 SEQUENCE
 ↓
得到 INTEGER r / s
 ↓
恢复为正整数
 ↓
去掉 DER 正数保护 00
 ↓
左侧补 0 到固定 32 Byte
 ↓
r[32] || s[32]
```

不能直接：

```c
memcpy(raw, der_r, 32);
```

因为 DER 中的 INTEGER 长度可能是：

```text
31
32
33
...
```

---

### 五、Raw → DER

反过来：

```text
r[32]
 ↓
去掉不必要前导 00
 ↓
如果最高 bit = 1，再补一个 00
 ↓
编码 INTEGER

s 同理
 ↓
套 SEQUENCE
```

本质就是：

```text
固定宽度无符号整数
↔
ASN.1 有符号 INTEGER
```

> [!important] 核心  
> **Signature `(r,s)` 是密码学对象。**
>
> `Raw r||s` 和 `DER SEQUENCE(r,s)` 只是它的两种编码。

## 第 7 章 · 第 4 课时

### Certificate：X.509 证书到底是什么？

证书并不只是“一个公钥文件”。

更准确地说：

> **证书是由签发者使用数字签名，把身份、公钥和相关属性可信绑定起来的数据结构。**

### 一、证书最外层

可以抽象为：

```text
Certificate
├── tbsCertificate
├── signatureAlgorithm
└── signatureValue
```

其中：

```text
TBS = To Be Signed
```

所以可以粗略理解为：

```text
证书正文
+
用什么算法签
+
签名结果
```

---

### 二、TBSCertificate

主体通常包含：

```text
TBSCertificate
├── version
├── serialNumber
├── signature
├── issuer
├── validity
├── subject
├── subjectPublicKeyInfo
└── extensions
```

其中最关键的几个概念：

```text
subject
→ 证书是谁的

issuer
→ 谁签发的

validity
→ 有效时间

subjectPublicKeyInfo
→ Subject 的公钥

extensions
→ 用途、约束和其他扩展
```

---

### 三、Subject 与 Issuer

通常：

```text
Subject = 证书持有者

Issuer = 证书签发者
```

自签名证书中可能：

```text
Subject = Issuer
```

并使用自己的私钥签名。

---

### 四、证书里的公钥仍然是 SPKI

结构：

```text
Certificate
 ↓
TBSCertificate
 ↓
SubjectPublicKeyInfo
 ├── AlgorithmIdentifier
 └── BIT STRING
        ↓
     EC Point
```

因此证书并没有创造一种“新的公钥”。

它只是把：

```text
SPKI
```

作为证书字段嵌入。

---

### 五、证书不包含私钥

正常 X.509 Certificate：

```text
有 Public Key

没有 Private Key
```

因此工程中通常：

```text
certificate.pem

private_key.pem
```

分别保存。

所谓：

```text
Certificate 与 Private Key 匹配
```

本质是：

```text
证书中的 P
=
dG
```

---

### 六、证书签名是谁生成的？

假设 CA 给 Server 发证书：

```text
Server Public Key
        ↓
放进 TBSCertificate
```

而：

```text
CA Private Key
        ↓
Sign(TBSCertificate)
        ↓
signatureValue
```

因此：

```text
Subject Public Key
```

与：

```text
生成 Certificate Signature 的 Private Key
```

通常属于不同实体。

验证证书时使用 Issuer 的公钥验证这份签名。

---

### 七、证书依然可以是 DER / PEM

```text
X.509 Certificate
        ↓ DER
Certificate Binary
        ↓ Base64
        ↓ PEM Wrapper
Certificate PEM
```

因此：

```text
DER Certificate
```

和：

```text
PEM Certificate
```

完全可能是同一张证书。

### 本课小结

```text
Certificate
├── 身份
├── Public Key
├── Validity / Attributes
└── Issuer Signature
```

证书真正完成的是：

```text
Identity
   ↕
Public Key
```

之间可验证的绑定。

## 第 7 章 · 第 5 课时

### 综合实战：从 PEM 一路剥到公钥和签名

这一课不增加新概念，只训练一个能力：

> **从外到内逐层拆数据。**

### 一、提取 Certificate Public Key

拿到：

```text
-----BEGIN CERTIFICATE-----
MIIC...
-----END CERTIFICATE-----
```

依次：

```text
PEM
 ↓
Base64 Decode
 ↓
DER
 ↓
ASN.1 Certificate
 ↓
TBSCertificate
 ↓
SubjectPublicKeyInfo
 ↓
BIT STRING
 ↓
00 || 04 || X || Y
```

其中：

```text
00
→ BIT STRING unused bits
```

而：

```text
04
→ Uncompressed EC Point
```

如果 API 需要：

```text
04 || X || Y
```

只删除前面的 `00`。

如果 API 需要：

```text
X || Y
```

还要继续删除 EC Point 前缀 `04`。

---

### 二、提取 Certificate Signature

证书结构：

```text
Certificate
├── TBSCertificate
├── signatureAlgorithm
└── signatureValue BIT STRING
```

继续：

```text
signatureValue
 ↓
BIT STRING
 ↓
DER Signature
 ↓
SEQUENCE
 ├── INTEGER r
 └── INTEGER s
 ↓
固定宽度转换
 ↓
r[32] || s[32]
```

于是同一张证书里，我们同时使用了前面几课的：

```text
PEM
Base64
DER
ASN.1
SPKI
BIT STRING
EC Point
Signature
INTEGER
```

但是每一层职责都不同。

---

### 三、统一的三问法

以后面对任何密码数据：

#### 第一问：它是什么对象？

```text
Public Key？
Private Key？
Signature？
Certificate？
Ciphertext？
```

#### 第二问：它是什么结构？

```text
X || Y？
04 || X || Y？
SPKI？
PKCS#8？
X.509？
SEQUENCE(r,s)？
```

#### 第三问：它是什么表示？

```c
Binary？
Hex？
Base64？
PEM？
```

最终模型：

```text
Object
+
Structure
+
Encoding / Representation
```

---

### 四、常见分析工具

查看证书内容：

```bash
openssl x509 -in device_cert.pem -text -noout
```

查看 ASN.1：

```bash
openssl asn1parse -in device_cert.pem -inform PEM
```

PEM 转 DER：

```bash
openssl x509 \
    -in device_cert.pem \
    -inform PEM \
    -out device_cert.der \
    -outform DER
```

查看 Binary Hex Dump：

```bash
xxd device_cert.der
```

注意：

```text
xxd 输出的是 Hex Dump

文件本身仍然是 DER Binary
```

### 五、第 7 章最终知识树

```text
Crypto Object
│
├── Public Key
│   ├── X || Y
│   ├── 04 || X || Y
│   └── SPKI
│
├── Private Key
│   ├── d
│   ├── ECPrivateKey
│   └── PKCS#8
│
├── Signature
│   ├── (r, s)
│   ├── Raw r || s
│   └── DER SEQUENCE(r,s)
│
└── Certificate
    └── X.509
        ├── TBSCertificate
        ├── signatureAlgorithm
        └── signatureValue

ASN.1 Object
    ↓
DER Binary
    ↓
Base64
    ↓
PEM
```

> [!important] 第 7 章最终结论  
> **密码学对象本身，与它的结构、编码和文本包装是不同层次。**
>
> 不要只问“这是 PEM 还是 DER”，还要继续问：
>
> **里面是什么对象？使用什么结构？我真正需要哪一层的数据？**
