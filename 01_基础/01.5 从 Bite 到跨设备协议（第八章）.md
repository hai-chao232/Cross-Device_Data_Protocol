# 第 8 章：从业务对象到跨设备 Wire Protocol

前 7 章已经解决了：

```text
数据是什么
内存怎样表示
Byte 怎样组织
Frame 怎样分界
对象怎样序列化
密码对象怎样编码
```

第 8 章只做一件事：

> **把这些知识组合成一套真正能用于 MCU ↔ Linux / PC 的完整工程模型。**

整章主线：

```text
Business Object
      ↓
Serialization
      ↓
Payload
      ↓
Protocol Frame
      ↓
Transport / Byte Stream
════════════ WIRE ════════════
Transport / Byte Stream
      ↓
Frame Parser
      ↓
Validation
      ↓
Payload Decode
      ↓
Business Object
```

## 第 8 章 · 第 1 课时

### 一份数据到底经历了什么？

### 一、从业务对象开始

假设 MCU 中：

```c
typedef struct {
    uint32_t id;
    int16_t  temperature;
    uint8_t  status;
} device_info_t;
```

业务意义：

```text
ID          = 0x12345678
Temperature = 25.3°C
Status      = Normal
```

这首先只是：

```text
Business Object
```

还不是协议。

---

### 二、Value、Memory、Wire 是三个概念

例如：

```c
uint32_t id = 0x12345678;
```

逻辑 Value：

```text
0x12345678
```

Little-Endian MCU 内存可能是：

```text
78 56 34 12
```

协议却可以规定：

```text
12 34 56 78
```

所以：

```text
Value
≠
Memory Representation
≠
Wire Representation
```

---

### 三、序列化得到 Payload

假设协议规定：

| Field       | Size   | Encoding          |
| ----------- | ------ | ----------------- |
| Device ID   | 4 Byte | Big Endian        |
| Temperature | 2 Byte | Big Endian，0.1°C |
| Status      | 1 Byte | 原值              |

那么：

```text
id          = 0x12345678
temperature = 253 = 0x00FD
status      = 1
```

得到：

```text
12 34 56 78 00 FD 01
```

这才是 Wire Payload。

---

### 四、Payload 还要放进 Frame

UART / TCP 上没有天然应用消息边界。

因此需要：

```text
Magic
Length
Command
Payload
CRC
```

最终：

```text
Business Object
    ↓
Serialization
    ↓
Payload
    ↓
Frame
    ↓
Byte Stream
```

---

### 五、接收端反过来

```text
RX Byte Stream
      ↓
Frame Parser
      ↓
Magic / Length / CRC
      ↓
Command / Payload
      ↓
Deserialization
      ↓
Business Object
```

不要：

```c
(device_info_t *)buffer
```

而应该按照 Wire Contract 显式解析。

---

### 六、密码数据只是 Payload 内部更深的一层

例如：

```text
SM2 Public Key
    ↓
Raw / SPKI / DER
    ↓
Payload
    ↓
Frame
    ↓
UART / TCP
```

如果需要文本形式：

```text
DER
 ↓
Base64
 ↓
PEM
```

所以：

```text
Raw / DER / PEM
Frame
UART / TCP
```

根本不处于同一层。

---

### 七、三个世界

#### 程序世界

```text
变量
类型
结构体
业务对象
```

#### 协议世界

```text
Endian
Length
Field
TLV
DER
Frame
CRC
Version
```

#### 传输世界

```text
Byte Stream
Bit
UART
USB
TCP
I2C / SPI
```

真正成熟的排错思维是：

> **先判断问题在哪一层，再查这一层的规则。**

跨设备问题先问：

1. 业务对象是什么？

2. 怎样序列化？

3. Wire Endian 是什么？

4. Byte 怎样组成 Frame？

5. Frame 怎样通过链路传输？

6. 接收端怎样验证并恢复？

7. Payload 内部是否还有密码格式？

## 第 8 章 · 第 2 课时

### 从零设计 MCU ↔ Linux / PC 二进制协议

设计目标：

> **稳定、明确、可扩展、可解析。**

### 一、先定义需求

假设支持：

```text
GET_VERSION
GET_DEVICE_INFO
GET_STATUS

GET_CONFIG
SET_CONFIG

SM4_ENCRYPT
SM4_DECRYPT

SM2_SIGN
SM2_VERIFY
```

那么协议必须回答：

```text
帧从哪里开始？
帧多长？
是什么命令？
Request 还是 Response？
请求与响应如何匹配？
Payload 在哪？
错误怎么检测？
协议怎么升级？
```

---

### 二、统一 Frame

```text
+---------+---------+-------+--------+----------+---------+---------+-------+
| Magic   | Version | Flags | Length | Sequence | Command | Payload | CRC16 |
+---------+---------+-------+--------+----------+---------+---------+-------+
| 2 Byte  | 1 Byte  | 1 Byte| 2 Byte | 2 Byte   | 2 Byte  | N Byte  | 2 Byte|
+---------+---------+-------+--------+----------+---------+---------+-------+
```

固定开销：

```text
12 Byte
```

---

### 三、Magic

规定：

```text
AA 55
```

用于：

```text
Frame Synchronization
```

Magic 只说明：

```text
这里值得尝试解析一帧
```

不表示整帧一定合法。

---

### 四、Version

例如：

```text
0x01 = Protocol V1
```

注意：

```text
Protocol Version
≠
Firmware Version
```

只有 Wire Format 或语义发生不兼容变化，才需要调整协议版本。

---

### 五、Flags

例如：

```text
bit0 = Response
bit1 = Error
bit2 = Encrypted
其他保留
```

这样：

```text
Flags   → 消息属性

Command → 业务含义
```

职责更清楚。

---

### 六、Length

这一套教学协议规定：

> **Length = 完整 Frame 总长度。**

因此：

```text
Frame Length
=
12 + Payload Length
```

协议文档绝不能只写：

```text
Length: 2 bytes
```

而应该写清：

```text
类型
Endian
覆盖范围
最小值
最大值
```

---

### 七、Sequence

作用：

```text
Request / Response 匹配
重试识别
必要时参与去重
```

响应应回显对应请求的 Sequence。

---

### 八、Command

建议固定明确编码：

```text
0x0101 GET_VERSION
0x0102 GET_DEVICE_INFO
0x0103 GET_STATUS

0x0201 GET_CONFIG
0x0202 SET_CONFIG

0x0301 SM4_ENCRYPT
0x0302 SM4_DECRYPT

0x0311 SM2_SIGN
0x0312 SM2_VERIFY
```

不要依赖 C enum 自动编号成为 Wire 值。

---

### 九、CRC

CRC 用于：

```text
检测传输过程中偶然损坏
```

但：

```text
CRC ≠ Security
```

攻击者可以修改数据并重新计算 CRC。

---

### 十、写成 Wire Contract

| Offset | Size | Field    | Encoding                 |
| ------ | ---- | -------- | ------------------------ |
| 0      | 2    | Magic    | `AA 55`                  |
| 2      | 1    | Version  | `0x01`                   |
| 3      | 1    | Flags    | Bit Field                |
| 4      | 2    | Length   | uint16 BE，总 Frame 长度 |
| 6      | 2    | Sequence | uint16 BE                |
| 8      | 2    | Command  | uint16 BE                |
| 10     | N    | Payload  | Command-specific         |
| 10+N   | 2    | CRC16    | 规定算法与覆盖范围       |

协议不能依赖：

```text
CPU Endian
sizeof(struct)
Compiler ABI
Pointer
Crypto Library Internal Object
```

---

### 十一、软件分层

发送：

```text
Business Layer
    ↓
Command Encoder
    ↓
Payload
    ↓
Frame Builder
    ↓
TX Driver
```

接收：

```text
RX Driver
    ↓
Frame Parser
    ↓
Protocol Validator
    ↓
Command Decoder
    ↓
Business Handler
```

> [!tip]  
> Protocol Layer 最好不关心底层到底是 UART、USB 还是 TCP。

## 第 8 章 · 第 3 课时

### 跨平台协议陷阱与安全解析

### 一、不要直接发送 Struct

```c
typedef struct {
    uint16_t cmd;
    uint32_t value;
    uint8_t  status;
} message_t;
```

成员相加只有：

```text
2 + 4 + 1 = 7 Byte
```

但：

```c
sizeof(message_t)
```

可能是：

```text
8
12
...
```

原因：

```text
Alignment
Padding
ABI
Compiler
```

因此：

```text
sizeof(struct)
```

不能定义跨设备协议。

---

### 二、Packed 也不是万能解法

`packed` 可以减少 Padding。

但解决不了：

```text
Endian
Unaligned Access
Compiler Extension
Version Compatibility
Field Semantics
```

甚至可能让成员处于未对齐地址，引发：

```text
性能下降
额外访存
BusFault / HardFault
```

---

### 三、显式 Encode / Decode

推荐：

```c
static void write_be16(uint8_t *p, uint16_t v)
{
    p[0] = (uint8_t)(v >> 8);
    p[1] = (uint8_t)v;
}

static uint16_t read_be16(const uint8_t *p)
{
    return ((uint16_t)p[0] << 8) |
           ((uint16_t)p[1]);
}
```

32-bit 同理。

不要：

```c
memcpy(buf, &value, sizeof(value));
```

也不要：

```c
uint32_t v = *(uint32_t *)&buf[3];
```

后者同时可能涉及：

```text
Endian
Alignment
Strict Aliasing
```

---

### 四、协议字段使用明确位宽

优先：

```text
uint8_t
uint16_t
uint32_t
uint64_t

int8_t
int16_t
int32_t
int64_t
```

不要让 Wire Format 依赖：

```text
int
long
size_t
pointer
```

在当前平台的宽度。

---

### 五、Length 永远不可信

外部收到：

```text
Length = 65535
```

不能直接：

```text
等待 65535 Byte
```

而应该：

```c
if (frame_len < PROTOCOL_MIN_FRAME_SIZE)
    return INVALID;

if (frame_len > PROTOCOL_MAX_FRAME_SIZE)
    return INVALID;
```

然后：

```c
if (buffered_size < frame_len)
    return NEED_MORE_DATA;
```

非常重要：

```text
Incomplete
≠
Invalid
```

---

### 六、推荐 Parser 顺序

```text
Search Magic
     ↓
Read Fixed Header
     ↓
Check Version
     ↓
Read / Validate Length
     ↓
Wait Complete Frame
     ↓
Check CRC
     ↓
Read Flags / Seq / Cmd
     ↓
Parse Payload
     ↓
Field Validation
     ↓
Validated Object
```

---

### 七、Payload 还要独立检查

即使：

```text
CRC OK
```

Payload 也可能是恶意数据。

例如：

```text
UID Length = 200

Payload Remaining = 20
```

必须拒绝。

安全解析常用：

```text
remaining
```

思路：

```c
if (remain < header_size)
    return ERR_TRUNCATED;

if (value_len > remain)
    return ERR_TRUNCATED;
```

---

### 八、UART / TCP 是 Byte Stream

不能：

```text
一次 read()
=
一帧
```

可能出现：

```text
拆包
粘包
半个 Header
两帧一起到达
```

因此需要：

```text
RX Buffer
+
持续 Frame Parser
```

---

### 九、错误后重新同步

发生：

```text
CRC Error
Invalid Length
Unsupported Version
Timeout
```

应：

```text
放弃当前 Candidate
 ↓
继续扫描
 ↓
寻找下一处 Magic
```

好的 Parser 必须能：

```text
自恢复
```

而不是要求：

```text
从上电开始一个 Byte 都不能出错
```

---

### 十、可信边界

推荐：

```text
External Bytes
     ↓
RX Buffer
     ↓
Frame Parser
     ↓
Length / CRC / Version
     ↓
Payload Bounds Check
     ↓
Field Validation

────────────────────
   Trust Boundary
────────────────────

     ↓
Validated Object
     ↓
Business Logic
```

> [!important]  
> 业务层最好只处理**经过验证的对象**，而不是直接操作外部 Byte。

## 第 8 章 · 第 4 课时

### 密码学数据怎样放进协议？

### 一、先分四层

以 SM2 Signature 为例：

```text
Crypto Object
    ↓
(r, s)
    ↓
Crypto Encoding
Raw r||s / DER
    ↓
Protocol Payload
    ↓
Frame
    ↓
UART / TCP / USB
```

所以：

```text
SM2 Algorithm
≠
SM2 Data Encoding
≠
Payload
≠
Frame
```

---

### 二、SM2 Public Key

常见表示：

```text
X || Y
→ 64 Byte

04 || X || Y
→ 65 Byte

SPKI DER
→ ASN.1 Binary

SPKI PEM
→ DER Text Wrapper
```

如果协议传 Raw，必须明确：

```text
Format
Length
X / Y Width
Endian
是否包含 0x04
```

例如：

```text
format = 0x04 || X || Y

length = 65 bytes

X = unsigned 32-byte big-endian

Y = unsigned 32-byte big-endian
```

---

### 三、SM2 Signature

Raw：

```text
r[32] || s[32]
```

协议应该写清：

```text
r / s
=
unsigned integer
big endian
32 Byte
left zero padded
```

如果传 DER：

```text
SEQUENCE {
    INTEGER r,
    INTEGER s
}
```

也必须明确写：

```text
Signature Format = DER
```

而不能只写：

```text
SM2 Signature
```

---

### 四、SM2 Ciphertext

常见组成：

```text
C1
C2
C3
```

可能存在：

```text
C1 || C3 || C2
```

以及：

```text
C1 || C2 || C3
```

这是一类经典互操作问题。

如果协议选择：

```text
Raw C1C3C2
```

可以规定：

```text
C1 = 65-byte uncompressed EC point
C3 = 32 Byte
C2 = N Byte
```

那么：

```text
[C1 65][C3 32][C2 N]
```

除此之外，还可能存在：

```text
ASN.1 DER SM2 Ciphertext
```

因此看到：

```text
SM2 Ciphertext
```

第一反应应该继续问：

```text
Raw / ASN.1？

C1C3C2 / C1C2C3？

C1 = 64 / 65 Byte？
```

---

### 五、SM4-CBC

SM4：

```text
Block Size = 16 Byte
Key Size   = 16 Byte
```

CBC 模式还需要：

```text
IV
Padding
Data Length
```

例如：

```text
+----------------+----------------+----------------+
| IV             | Data Length    | Plaintext      |
+----------------+----------------+----------------+
| 16 Byte        | 2 Byte         | N Byte         |
+----------------+----------------+----------------+
```

协议还要明确：

```text
Algorithm = SM4
Mode      = CBC
Padding   = PKCS#7
IV        = Payload 提供
Key       = key_id 选择
```

不能把这些参数藏在程序默认值里。

---

### 六、长期 Key 通常使用 Key ID

更常见：

```text
Request:
Key ID
IV
Data
```

设备内部：

```text
Key ID
 ↓
Key Slot
 ↓
Real Key
```

而不是每次都：

```text
Raw Key
+
Data
```

一起传。

---

### 七、CRC 与密码认证

即使 Payload 已加密：

```text
Frame CRC
```

仍然可以保留，用于快速检测偶然传输错误。

但是：

```text
CRC
≠
Authentication
```

真正防篡改需要：

```text
MAC
Signature
AEAD
```

如果使用 AEAD，则还要明确：

```text
Nonce / IV
Ciphertext
Tag
AAD
Authentication Coverage
```

---

### 八、Sequence 与 Anti-Replay

Sequence 首先用于：

```text
Request / Response Matching
```

如果配合认证与状态管理，也可以参与防重放。

例如：

```text
counter > last_counter
```

但：

```text
有 Sequence
```

不等于：

```text
已经完成 Anti-Replay
```

---

### 九、格式选择

内部二进制协议通常优先：

```text
Raw Binary
或
DER
```

调试：

```text
Hex Dump
```

文本环境：

```text
Base64
PEM
```

> [!tip]  
> 如果协议本身已经能够传任意 Binary，就没必要为了“看起来方便”再把数据先变成 PEM。

## 第 8 章 · 第 5 课时

### 终极综合实战：PC 请求 MCU 完成 SM2 签名

需求：

```text
PC / Linux
    │ UART / USB CDC / TCP
    ↓
MCU Crypto Device
```

PC 请求：

> 使用 Key Slot 2 的 SM2 Private Key，对 `"Hello"` 签名。

User ID：

```text
1234567812345678
```

响应规定：

```text
Raw Signature
=
r[32] || s[32]
```

---

### 一、Business Object

```c
typedef struct {
    uint8_t key_id;

    const uint8_t *user_id;
    uint8_t user_id_len;

    const uint8_t *message;
    uint16_t message_len;
} sm2_sign_request_t;
```

不能：

```c
send(fd, &req, sizeof(req));
```

因为：

```text
user_id
message
```

是本机 Pointer。

Pointer 跨设备没有意义。

再次说明：

```text
C Object
≠
Wire Object
```

---

### 二、Request Payload

规定：

```text
+---------+---------+----------+-----------+----------+
| Key ID  | UID Len | UID      | Msg Len   | Message  |
+---------+---------+----------+-----------+----------+
| 1 Byte  | 1 Byte  | M Byte   | 2 Byte    | N Byte   |
+---------+---------+----------+-----------+----------+
```

其中：

```text
Message Length
=
uint16 Big Endian
```

数据：

```text
Key ID = 2
```

编码：

```text
02
```

UID：

```text
"1234567812345678"
```

ASCII / UTF-8 Byte：

```text
31 32 33 34 35 36 37 38
31 32 33 34 35 36 37 38
```

UID Length：

```text
16
=
0x10
```

Message：

```text
"Hello"
```

Byte：

```text
48 65 6C 6C 6F
```

Message Length：

```text
5
=
00 05
```

最终 Payload：

```text
02 10
31 32 33 34 35 36 37 38
31 32 33 34 35 36 37 38
00 05
48 65 6C 6C 6F
```

Payload Length：

```text
25 Byte
```

---

### 三、Frame

固定开销：

```text
12 Byte
```

因此：

```text
Frame Length
=
12 + 25
=
37
=
0x0025
```

假设：

```text
Magic    = AA 55

Version  = 01

Flags    = 00

Sequence = 00 2A

Command  = 03 11
```

完整 Frame：

```text
AA 55
01
00
00 25
00 2A
03 11
[Payload 25 Byte]
[CRC16]
```

Wire 上已经没有：

```text
sm2_sign_request_t
```

只有：

```text
Byte
```

---

### 四、接收不一定一次完整

发送端：

```c
write(fd, frame, 37);
```

并不意味着接收端一定一次拿到：

```text
37 Byte
```

可能：

```text
第 1 次：5 Byte
第 2 次：9 Byte
第 3 次：剩余 Byte
```

Parser 应返回：

```text
NEED_MORE_DATA
```

而不是：

```text
ERROR
```

更不能因为数据暂时没收齐就清空 Buffer。

---

### 五、Frame Validation

顺序：

```text
Magic
 ↓
Version
 ↓
Length Range
 ↓
Frame Complete?
 ↓
CRC
 ↓
Flags
 ↓
Sequence
 ↓
Command
```

只有通过这些检查，才进入 Payload Parser。

---

### 六、Payload Validation

继续：

```text
Key ID
 ↓
UID Length
 ↓
UID
 ↓
Message Length
 ↓
Message
```

每一步：

```text
先检查 remaining
再读取
```

最终恢复：

```text
key_id      = 2

user_id     = "1234567812345678"

user_id_len = 16

message     = "Hello"

message_len = 5
```

此时才得到：

```text
Validated Request
```

然后进入真正的 SM2 业务逻辑。

---

### 七、Crypto Library Adapter

SM2 算法最后得到：

```text
Signature = (r, s)
```

不同密码库可能输出：

```text
内部对象
Raw r||s
DER Signature
```

协议不能依赖某个密码库当前的内部表示。

应该做：

```text
Crypto Library
      ↓
Format Adapter
      ↓
Protocol Format
```

例如始终统一成：

```text
r[32] || s[32]
```

这样即使未来更换密码库：

```text
Wire Format
```

也不用改变。

---

### 八、Response Payload

可以定义：

```text
+----------+--------+---------+-----------+
| Status   | Format | Sig Len | Signature |
+----------+--------+---------+-----------+
| 2 Byte   | 1 Byte | 2 Byte  | N Byte    |
+----------+--------+---------+-----------+
```

例如：

```text
Status:
00 00 = SUCCESS

Format:
01 = RAW_R_S
02 = DER

Sig Length:
00 40 = 64 Byte
```

成功返回：

```text
00 00
01
00 40
[r 32 Byte]
[s 32 Byte]
```

Payload Length：

```text
69 Byte
```

Response 应保持：

```text
Sequence = 00 2A

Command = 03 11
```

这样 PC 可以匹配原请求。

### 十、最终排错树

出现问题时逐层排查：

```text
Physical Layer OK?
        ↓
Transport Bytes OK?
        ↓
Frame OK?
        ↓
CRC OK?
        ↓
Payload Bounds OK?
        ↓
Serialization / Endian OK?
        ↓
Crypto Format OK?
        ↓
Algorithm Parameters OK?
        ↓
Business Logic OK?
```

典型现象：

| 问题                           | 优先检查                               |
| ------------------------------ | -------------------------------------- |
| UART 波形不对                  | Clock / Baudrate / Voltage / Wiring    |
| Byte 正确但找不到 Frame        | Magic / Length / Buffer / Parser       |
| CRC 总失败                     | CRC 参数、覆盖范围、Endian             |
| `12345678 → 78563412`          | Endian                                 |
| 两边 Struct 大小不同           | Padding / Alignment / ABI              |
| Base64 能解但 OpenSSL 不认     | DER / ASN.1                            |
| SM2 64 Byte Signature 不被接受 | Raw `r                                 |
| SM2 Ciphertext 解密失败        | C1C3C2 / C1C2C3、Raw / ASN.1           |
| 签名、公钥都正确但验签失败     | User ID、Message、Hash Input、Encoding |
